# StitchProof: Build Spec

> Build milestone by milestone, in order. Never push directly to main.

## 0. Context

- **What:** StitchProof is a local tech-editor for crochet patterns. A small open-weight model, fine-tuned on Tinker, translates each written row of a pattern into a precise stitch program. Plain code then simulates the stitch counts row by row and flags every place where the stated count does not match what the instructions actually produce.
- **Why it exists:** submission to the DEV Hacktoberfest 2026 Open-Source AI Challenge, Week 2: "Side Hustle" (build something with open-weight models that someone would actually pay for).
- **Prize categories entered:** Best Use of Tinker (primary), Best Use of GitHub Copilot (GitHub Actions + Copilot PR reviews). Gemma only as an optional stretch (section 16).
- **Deadline:** submissions close Oct 18, 11:59 PM PDT = **Mon Oct 19, ~12:29 PM IST**. Target: post published **Sun Oct 18 night IST**. Monday morning is buffer only.
- **Challenge rules:** brand-new repo, started and finished inside the challenge window (Oct 12 to 18). No reused code from other projects. Entrant is 18+.
- **Owner:** Heet (GitHub: HeetRanpura). Machine: MacBook with Apple M4, 16 GB RAM, limited free disk.

### The story the project must support
- AI and crochet are a well-known bad mix: general chatbots produce crochet instructions that don't work.
- Pattern designers sell PDF patterns on Etsy and Ravelry and pay human tech editors to verify every stitch count before publishing. Errata are a known, recurring problem.
- StitchProof's key design choice: **the model only translates notation; code does all the counting.** So every flag is verifiable, and the fine-tune's improvement is measured by code, not by opinion.
- Headline comparison for the post: how many seeded errors each approach catches, and how many false alarms it raises on correct rows. Approaches: (A) base model asked directly, (B) large model asked directly (reference), (C) base model + simulator, (D) fine-tuned model + simulator.

## 1. Product

Two modes, one engine.

- **Designer mode (paid tier in the business story):** paste or upload a full pattern (.txt, .md, or text-based .pdf). Get a row-by-row table: row label, original text, parsed program in plain words, stitches available, stitches used, stitches made, stated count, status (OK / ERROR / WARNING / CAN'T CHECK), and an explanation. Plus a "silhouette" chart of stitch counts per row, and a downloadable report (Markdown and HTML).
- **Maker mode (free tier):** a crocheter stuck mid-project enters the previous row's stitch count and pastes one row. Answer: "The pattern says X. These instructions make Y from your Z stitches." This answers "is the pattern wrong, or am I?"
- **Business framing (for README and post only):** makers free (distribution), designers pay per pattern check or a small monthly fee. Do not invent prices or claims in code or docs; leave pricing as Heet's stated hypothesis.

## 2. Non-negotiables

1. **Privacy:** patterns are processed only on the local machine in the app. No telemetry. Tinker is used only for training and for evaluating on synthetic or permitted data.
2. **Never commit real patterns.** `data/real/` is gitignored. Never open, print or log files in `data/real/`; Heet runs real-data commands himself.
3. **No copyrighted patterns in the repo or in training data.** Training and synthetic eval data are generated by our own code. Do not scrape or download published patterns.
4. **Code decides counts.** The model never computes or "corrects" counts. It transcribes exactly what the text says, including wrong numbers.
5. **Honest evaluation:** the same prompt, the same eval sets and the same parser for base and fine-tuned. Never tune on eval sets. Every percentage is reported with its count (e.g. 83.3% (50/60)).
6. **Can't check is an answer.** Anything out of scope is marked CAN'T CHECK with a reason, never guessed.
7. Secrets in `.env` (`TINKER_API_KEY`), never committed. Provide `.env.example`.
8. License: MIT for code. README notes the base model's own license.
9. **Budget:** before any Tinker run, check the remaining account credit and report it. Print a cost estimate before every generation or training run. Stop and ask if a single run would exceed US$5 or would leave less than US$1 of credit. Size datasets to fit the remaining credit.

## 4. Counting conventions

See [CONVENTIONS.md](CONVENTIONS.md) for the full, reviewed text. Summary: US terms only in v1; one-in-one stitches; increases; decreases; loop modifiers never change counts; magic ring; foundation chain and skipped chains; turning chains; joined rounds; "around/across/to end" must use all stitches; repeats; row ranges; stated-count formats; notes ignored; out-of-scope constructs are CAN'T CHECK.

## 5. Stitch program schema (`schema.py`)

`LineProgram` with `kind` (row / round / foundation / note / unsupported), `label`, `range_start`, `range_end`, `start` (continue / magic_ring / chain, with chain_count, skip_chains, skipped_count_as_stitch), `ops` (work, into_one, together, skip, work_rest, turning_chain, repeat), `must_use_all`, `stated_count`, `unsupported_reason`.

Program JSON is the model's only output. `parse_output.py` must handle: plain JSON, JSON in ``` fences, trailing text, invalid enum values, missing fields. A parse failure counts as wrong in every metric.

## 6. Simulator (`simulate.py`)

Input: a list of `LineProgram` in order. Output: one result per line with `available`, `used`, `made`, `stated`, `status`, `codes`, `explanation`.

| Code | Level | Meaning |
| --- | --- | --- |
| COUNT_MISMATCH | ERROR | made != stated |
| OVERFLOW | ERROR | instructions need more stitches than available |
| LEFTOVER | ERROR | must_use_all and stitches left unworked |
| REPEAT_REMAINDER | ERROR | an "around" repeat does not divide the available stitches |
| NO_STATED_COUNT | WARNING | row has no stated count |
| CANT_CHECK | INFO | unsupported line, or previous count unknown because of an earlier unsupported line |

Explanations are deterministic templates, never generated by a model, and always include the numbers.

## 7. Shared prompt (`prompts.py`)

One system prompt + one user template, used identically for base-model eval, training data, fine-tuned eval and the app. Input per line: short pattern header, previous line (context only), current line. Output: exactly one `LineProgram` JSON object. Transcribe exactly; never correct counts; notes become "note"; out of scope becomes "unsupported" with a reason. Keep the system prompt under ~400 tokens. Qwen3.5 answers without a thinking block.

## 8. Synthetic data (`generate/`)

Pipeline: pattern structure (code) -> gold programs (code) -> render text (code templates, plus teacher paraphrase for a share) -> seed errors (code, into both text and gold) -> simulate gold (code) to get labels -> JSONL.

- Shapes: sphere, cylinder, cone, rectangle, triangle/trapezoid, mixed-stitch rows, interleaved notes; 6 to 25 lines.
- Renderer: many notation styles per construct. Hold out 4 styles and at least one shape variant (cones) for eval only.
- Teacher paraphrase for ~35% of patterns (`openai/gpt-oss-120b`), one output line per input line, labels and numbers preserved, validated in code.
- Error seeding: WRONG_STATED, WRONG_REPEAT_TIMES, WRONG_RUN_LENGTH, WRONG_FOUNDATION, NON_DIVISIBLE_AROUND, MISSING_STATED. About 50% of patterns get 1 or 2 seeded errors.
- Splits: train ~3,000 lines, val ~300 lines, eval_synth ~60 patterns from held-out styles and shapes only. Fixed seed, reproducible.

## 9. Out-of-generator and real sets

- OOD: 25 patterns whose structure and gold come from our generator, but whose text is written by a different model family on Tinker, free-form.
- Real (`data/real/`, gitignored): permitted drafts, labelled by Heet with `label_real.py`. Never logged, never opened by automation.

## 10. Baselines and evaluation

| ID | Approach | What it shows |
| --- | --- | --- |
| A | Base Qwen3.5-4B, direct check | "AI can't crochet", the hook |
| B | Teacher (large model), direct check | Reference only, labelled as such |
| C | Base Qwen3.5-4B, line parse + simulator | Fair baseline for the fine-tune |

Metrics, each with counts: errors caught (headline), false alarms (headline), pattern-level accuracy, line parse exact match, count-equivalence, stated-count faithfulness, valid JSON rate, can't-check rate.

## 11. Training

Qwen/Qwen3.5-4B LoRA rank 32, cookbook LR, 2 epochs, batch 8, max length 2048, assistant-only loss. Print estimated tokens and cost first. Save the final sampler checkpoint path to `train/runs.json`.

Repo `HeetRanpura/stitchproof`, default branch `main`. ## 15. Milestones

- **M1 Engine** (`m1-engine`): scaffold, schema, simulator, segmenter, parser, canonicaliser, CONVENTIONS.md, tests, CI.
- **M2 Data pilot** (`m2-data`): shapes, renderer, errors, prompt; 40-pattern pilot; baselines A, C (and B on 15 if credit allows). Go/no-go: if C already catches 90%+ with <= 5% false alarms, propose harder notation.
- **M3 Full dataset** (`m3-dataset`): paraphrase, full splits, OOD set, spot-check.
- **M4 Training + eval** (`m4-train`): sft.py, train v1, evaluate A/B/C/D on eval_synth and ood, summary.md, eval.yml.
- **M5 Export** (`m5-export`): adapter download, merge, GGUF, local equivalence check.
- **M6 Local app** (`m6-app`): local_model.py, report_export.py, ui.py.

## 16. Stretch (optional)

- **Gemma 4 reader:** for photos or scans of printed patterns, a local Gemma 4 vision model (Ollama; prefer the E4B size) transcribes the image to text before parsing. Fall back to "please paste text" if unavailable. Qualifies for Best Use of Gemma only if it actually works.

## 17. Acceptance criteria

- [ ] `pytest` passes, including all golden tests and one test per error code.
- [ ] `build_dataset` reproduces splits from a fixed seed.
- [ ] Approaches A, C and D evaluated on eval_synth and ood; results with counts in summary.md.
- [ ] D beats C on errors caught without a higher false-alarm rate, or the results say plainly that it doesn't.
- [ ] The app runs locally with no network after the model download, or the fallback is clearly labelled.
- [ ] No real patterns, names or private text in git history.
- [ ] README and post material contain only numbers that exist in eval/results.

## 18. Out of scope (do not build)

Accounts, payments, cloud hosting, pattern generation, knitting, charts or diagrams as input, multi-size patterns, lace and chain spaces, UK terms, mobile apps, and anything that writes or "fixes" a designer's pattern automatically. StitchProof flags problems; the designer decides.

## 19. Limitations to state honestly

- Training data is synthetic; the real-pattern test set is small.
- v1 covers US terms, amigurumi rounds and flat rows with common stitches only; everything else is marked CAN'T CHECK.
- Counting conventions vary between designers; StitchProof follows CONVENTIONS.md.
- It checks stitch math only, not gauge, fit or the look of the finished piece.
- Other crochet tools exist (AI pattern generators, chart renderers, stitch counters); StitchProof's difference is automated, local checking of a designer's own draft, with a measured fine-tune.
